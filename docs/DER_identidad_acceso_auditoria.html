Identidad, acceso y auditoría

Diccionario de datos, relaciones y reglas de seguridad de las 6 tablas propias (más auth.users, de Supabase) que sostienen usuarios, roles, permisos y auditoría, para tener en cuenta al escribir el SQL.

6 tablas + auth.usersPostgreSQL / SupabaseRLS en todasEsquema publicAprobado 2026-11-20
Criterio de diseño: cada campo existe porque la aplicación lo necesita. email, contraseña, último ingreso y bloqueo real viven en auth.users (Supabase) y no se duplican. Quién asignó un rol y cuándo se obtiene de audit_logs, no de columnas extra. Los tipos y longitudes son propuestas para el SQL.

1. Diccionario de datos

Convenciones: uuid para identificadores; text con CHECK de longitud en lugar de varchar(n); timestamptz para instantes; enum de PostgreSQL para estados cerrados. Todo updated_at se mantiene con un trigger set_updated_at.

1.1 profiles

public1:1 con auth.users

Datos propios de la aplicación para cada cuenta. Reemplaza active y archived_at por un solo status, y elimina notes.

Campo Tipo Nulo Clave / regla Uso
id uuid No PK y FK → auth.users(id) ON DELETE CASCADE Mismo UUID que la cuenta de Auth.
full_name text No CHECK length(btrim(full_name)) BETWEEN 2 AND 120 Nombre visible. Obligatorio: el alta lo exige.
phone text Sí CHECK length ≤ 30 Contacto. Texto por prefijos y formatos.
avatar_path text Sí Ruta en Storage, no URL Foto opcional. Se guarda la ruta porque la URL puede cambiar.
status profile_status No DEFAULT 'pending'. Enum: pending | active | inactive pending: invitado sin completar el alta. active: puede operar. inactive: bloqueado y archivado.
created_at timestamptz No DEFAULT now() Alta del perfil.
updated_at timestamptz No DEFAULT now() + trigger Última modificación.

Índice: (status) para listados filtrados. Migración: status = case when archived_at is not null or not active then 'inactive' else 'active' end; se pasan los invitados pendientes a pending.

1.4 role_permissions

publicN:M
Campo Tipo Nulo Clave / regla Uso

La PK compuesta impide asignar dos veces el mismo permiso. Índice: (permission_code, role_id) para consultar a qué roles pertenece un permiso. Sin assigned_at.

1.5 user_roles

publicN:M
Campo Tipo Nulo Clave / regla Uso
user_id uuid No PK parcial + FK → profiles(id) ON DELETE CASCADE Usuario que recibe el rol.
role_id uuid No PK parcial + FK → roles(id) ON DELETE RESTRICT Rol asignado.

Un usuario puede tener varios roles (por ejemplo, admin y delivery). Sin assigned_by ni assigned_at: ambos datos están en audit_logs. Si el panel necesita mostrar “tiene el rol desde…”, se agrega assigned_at. Índice: (role_id, user_id).

1.6 audit_logs

publicsolo inserción
Campo Tipo Nulo Clave / regla Uso
id bigint No PK, GENERATED ALWAYS AS IDENTITY Orden cronológico y volumen alto: bigint es más liviano que uuid.
actor_id uuid Sí FK → auth.users(id) ON DELETE SET NULL Quién actuó. NULL si fue el servidor o una migración (sin auth.uid()). Referencia a auth.users y no a profiles: es el mismo UUID, no depende del orden de creación de las tablas y es la misma referencia que usa categories.updated_by.

Índices: (created_at desc), (table_name, record_id), (actor_id). El último es necesario porque la FK de actor_id lo requiere para borrados eficientes.

Entidad externa: auth.users es nativa de Supabase y no se crea desde las migraciones. Aporta email, last_sign_in_at, banned_until (bloqueo real) y raw_app_meta_data. Son 6 tablas propias en este dominio más esta entidad externa, que es el punto de partida de las relaciones.

2. Relaciones y cardinalidades

Relación Cardinalidad Cómo se implementa Lectura
auth.users — profiles 1 — 1 profiles.id es PK y FK a auth.users.id Cada cuenta tiene un perfil; el perfil no existe sin cuenta. Un trigger lo crea al registrarse el usuario.
profiles — user_roles 1 — N FK user_roles.user_id Un usuario puede tener varios roles, o ninguno.
roles — user_roles 1 — N FK user_roles.role_id Un rol se asigna a muchos usuarios.
profiles N — M roles N — M Tabla puente user_roles Resuelve la relación muchos a muchos entre usuarios y roles.
roles — role_permissions 1 — N FK role_permissions.role_id Un rol concede varios permisos.
permissions — role_permissions 1 — N FK role_permissions.permission_code Un permiso puede estar en varios roles.
roles N — M permissions N — M Tabla puente role_permissions Resuelve la relación muchos a muchos entre roles y permisos.
auth.users — audit_logs 0..1 — N FK audit_logs.actor_id (nullable) Un usuario genera muchos eventos; un evento puede no tener actor.
audit_logs → otras tablas Lógica table_name + record_id (sin FK) Referencia polimórfica a propósito: el historial debe sobrevivir al borrado del registro original.

Cadena de autorización: usuario → user_roles → roles → role_permissions → permissions. Un permiso se aplica solo si el perfil está active y el rol tiene is_active = true.

3. Seguridad que debe demostrarse

Reglas a incorporar cuando se escriba el SQL, cada una con su motivo.

3.1 Reglas que acompañan al esquema

  1. Estado y login. Al pasar profiles.status a inactive, el servidor también pone banned_until en auth.users; al reactivar, lo limpia. Por qué: el estado de la aplicación no cierra sesiones ni impide renovar tokens. Solo el bloqueo de Auth corta el acceso de verdad.
  2. Auditoría de seguridad. Triggers de auditoría en profiles, roles, user_roles y role_permissions (y en permissions por si se edita el catálogo). Por qué: al quitar assigned_by y assigned_at, el trigger es la única forma de saber quién dio cada rol y cuándo.
  3. record_id en claves compuestas. El trigger arma "user_id:role_id" y "role_id:permission_code" porque no existe columna id. Por qué: sin esto el trigger genérico guardaría NULL y el evento sería imposible de rastrear.
  4. is_system. Las RPC y un trigger BEFORE UPDATE OR DELETE rechazan borrar roles del sistema, cambiarles el code o desactivarlos. Por qué: el código depende de admin; si se renombra, se rompe el acceso al panel. Los demás roles (por ejemplo staff y delivery) se protegen igual cuando se siembren con su módulo. La regla va en trigger y no solo en RPC para que no se pueda saltear por la Data API.
  5. audit_logs.actor_id. Es NULL cuando actúa el servidor o una migración. Con ON DELETE SET NULL el historial sobrevive al borrado de la cuenta. Por qué: un registro de auditoría que desaparece con el usuario no sirve como evidencia.

3.2 Reglas de borrado en cascada (ON DELETE)

FK Regla Por qué
profiles.id → auth.users.id CASCADE Un perfil sin cuenta no tiene sentido ni puede usarse. En la práctica la baja normal es status = inactive; borrar la cuenta queda para casos excepcionales.
user_roles.user_id → profiles.id CASCADE Las asignaciones de un usuario eliminado quedan huérfanas. El evento de borrado queda en audit_logs.
user_roles.role_id → roles.id RESTRICT Impide borrar un rol en uso y dejar usuarios sin permisos sin darse cuenta. Se debe desasignar primero (o desactivar el rol).
role_permissions.role_id → roles.id CASCADE Los permisos de un rol borrado no tienen utilidad; borrar el rol ya está protegido por RESTRICT.
role_permissions.permission_code → permissions.code RESTRICT en delete, CASCADE en update Quitar un permiso del catálogo debería ser una decisión consciente. Renombrar un código se propaga solo.
audit_logs.actor_id → auth.users.id SET NULL Conserva el historial aunque se elimine al actor. Nunca CASCADE: borraría la evidencia.
categories.updated_by → auth.users.id SET NULL Hoy es NO ACTION e impide borrar un usuario que haya modificado categorías. Se corrige en la migración de categories a permisos.

3.3 Funciones auxiliares y triggers

  • private.has_permission(code) y private.has_role(code). SECURITY DEFINER, STABLE, SET search_path = public, auth, esquema private sin acceso desde la API. Verifican perfil active, rol is_active y relación completa. Por qué: las políticas de user_roles consultan tablas que a su vez tienen RLS; sin SECURITY DEFINER habría recursión infinita. El search_path fijo evita secuestro de funciones.
  • Política de uso. Las políticas RLS verifican permisos (has_permission('users.manage')) y no nombres de rol; private.is_admin() queda como atajo. Por qué: permite crear roles personalizados sin tocar las políticas.
  • set_updated_at en profiles y roles: garantiza que updated_at no dependa del cliente.
  • handle_new_auth_user (AFTER INSERT ON auth.users): crea el perfil con status = 'pending' si el alta viene de invitación (onboarding_required) y 'active' en otro caso. Por qué: evita perfiles faltantes y que un invitado opere antes de completar el alta. La marca de invitación debe viajar en raw_app_meta_data, que el usuario no puede editar, y el registro público de Auth debe estar desactivado.
  • Trigger de auditoría genérico SECURITY DEFINER: escribe en audit_logs con permisos propios, ya que los usuarios no pueden insertar directamente.
  • Protección anti-escalada (BEFORE INSERT/UPDATE/DELETE en user_roles y role_permissions): exige roles.manage y bloquea que un usuario se asigne roles o permisos a sí mismo. Por qué: un administrador comprometido no debería poder entregarse más poder sin dejar de ser detectable. Debe permitir migraciones y seed (sin auth.uid()).
  • Guardia del último administrador: impide quitar el rol admin, inactivar o borrar al último usuario con admin.access. Por qué: evita quedarse sin nadie que pueda gestionar el sistema.
  • Defensa por Data API: REVOKE EXECUTE de las funciones de trigger a public, anon y authenticated, para que no puedan invocarse a mano.

3.4 Row Level Security

RLS activado en las 6 tablas. Primero REVOKE ALL a anon y authenticated; luego solo los GRANT necesarios. Las escrituras sensibles se hacen por RPC SECURITY DEFINER con validación interna.

Tabla SELECT INSERT / UPDATE / DELETE Por qué
profiles Propio (auth.uid() = id) o users.manage Sin GRANT directo. El usuario edita full_name, phone, avatar_path mediante RPC; status solo lo cambia users.manage Si el usuario pudiera hacer UPDATE directo, podría reactivarse (status) o cambiar campos protegidos. RLS controla filas, no columnas.
roles Cualquier usuario autenticado con perfil activo Solo roles.manage, vía RPC (admin_create_role, admin_update_role, admin_delete_role) El panel necesita mostrar nombres de rol; modificarlos es privilegio administrativo.
permissions roles.manage Ninguno desde la API; solo migraciones Es un catálogo sembrado por código. Editarlo en runtime permite inventar permisos que nada verifica.
role_permissions roles.manage Solo vía RPC con roles.manage Define quién puede hacer qué: la tabla más sensible del dominio.
user_roles Propias filas o users.manage Solo vía RPC con users.manage, sin autoasignación El usuario necesita saber sus roles para armar el menú, pero no cambiarlos.
audit_logs audit.read (o admin) Ninguno desde la API; solo triggers. REVOKE UPDATE, DELETE, TRUNCATE a todos los roles Un registro de auditoría que se puede editar o borrar no sirve como evidencia.
  • Rendimiento: en las políticas se escribe (select auth.uid()) y (select private.has_permission(...)) para que se evalúen una vez por consulta y no por fila.
  • Sesiones antiguas: las políticas exigen perfil active; así una sesión vigente de un usuario inactivo ya no lee datos aunque el token siga válido.
  • Contrato de la app: get_current_access_context() devuelve usuario, email, roles y permisos en una sola llamada; el frontend decide qué mostrar, pero la seguridad real la imponen RLS y las RPC.
  • Realtime: no publicar estas tablas. Expondrían cambios de permisos y auditoría a canales que no pasan por las RPC.
  • Verificación: cada política debe tener su prueba: usuario sin rol, inactivo, pending y admin intentando leer y escribir cada tabla.

3.5 Decisiones sobre retención y datos sensibles

  • Retención de audit_logs: sin purga por ahora. El volumen de estas tablas es bajo. Se revisa antes de auditar tablas con más movimiento (por ejemplo, pedidos); si se agrega purga, requerirá una excepción explícita al REVOKE DELETE.
  • Datos sensibles en old_data y new_data: hoy ninguna tabla auditada tiene campos sensibles. El trigger debe poder excluir columnas por tabla (tokens, claves) si alguna tabla futura las tuviera.
